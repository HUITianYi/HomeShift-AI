# 系统架构与 Agent 原理

> 本文讲清楚两件事：**Agent 循环里每一步发生了什么**，以及**每个数字是怎么算出来的**。

## 1. Agentic Loop：核心中的核心

`agent/core.py` 实现了标准的 tool-use 循环（与 Anthropic Messages API 原生协议一致）：

```
用户请求
   │
   ▼
┌──────────────────────────────────────────────┐
│  LLM 推理（携带系统提示词 + 12 个工具定义 + 完整对话历史）│
└──────────────────────────────────────────────┘
   │
   ├── stop_reason == "tool_use" ──► 本地执行工具（可能多个并行）
   │                                    │
   │                                    ▼
   │            工具结果以 tool_result 消息追加到对话历史 ──► 回到 LLM 推理
   │
   └── stop_reason == "end_turn" ──► 输出最终回答，回合结束
```

以 `diagnose` 为例，一次真实运行的完整轨迹：

```
第1轮  LLM: "先读取画像和数据" + tool_use(get_household_profile)
      本地: 执行 → 返回画像 JSON
第2轮  LLM: tool_use(get_usage_summary, days=30)
      本地: 执行 → 30 天日用电 + 月度电费估算
第3轮  LLM: tool_use(get_weather_summary, days=30)     ← 为什么查天气？解释空调用电
第4轮  LLM: tool_use(disaggregate_usage, days=28)      ← 核心诊断
第5轮  LLM: tool_use(get_tariff_info)                  ← 换算金额
第6轮  LLM: tool_use(get_carbon_info)                  ← 换算碳排
第7轮  LLM: stop_reason=end_turn，输出完整诊断报告
```

**护栏**（`core.py`）：
- `max_tool_rounds`（默认 16）限制单回合工具轮数，防失控；
- 工具抛异常时不崩溃，而是以 `is_error: true` 的 tool_result 交还 LLM 自行调整；
- `stop_reason == "refusal"`（安全分类器拒绝）时输出友好提示；
- 助手消息（含 thinking 块）**原样**追加回历史，符合 Claude API 多轮回传要求。

## 2. 工具层：12 个工具 = Agent 的能力边界

工具即能力边界——Agent 能做什么、不能做什么，全部由 `agent/tools.py` 定义（安全性由此而来）：

| 类别 | 工具 | 作用 |
| --- | --- | --- |
| 感知 | `get_household_profile` | 家庭画像（含**舒适硬约束**） |
| 感知 | `get_usage_summary` | 电表数据摘要 + 月度电费折算 |
| 感知 | `get_weather_summary` | 气温与制冷度时（解释空调用电） |
| 感知 | `get_tariff_info` / `get_carbon_info` | 电价方案 / 电网碳因子 |
| 分析 | `disaggregate_usage` | **负载分解**：总电表 → 六大类别 |
| 分析 | `simulate_savings` | **节能模拟**：量化每个候选动作的收益 |
| 行动 | `save_plan` | 保存计划（自动版本化，记录基线期） |
| 行动 | `track_progress` | **天气归一化**效果追踪 |
| 记忆 | `record_feedback` / `get_memories` | 写入/读取长期记忆 |
| 记忆 | `get_active_plan` | 当前生效计划 |

每个工具 = JSON Schema 定义（给 LLM 看，`description` 写明什么时候该用）+ 本地执行函数（`dispatch_tool`）。工具返回 JSON，作为 `tool_result` 回传。

## 3. LLM 抽象层：一套循环，两种大脑

```
Agent.run_task()
     │  只依赖 LLMClient 接口
     ▼
┌───────────────┐      ┌─────────────────────────────┐
│ AnthropicClient│      │ MockLLMClient               │
│ 真实 Claude    │      │ 场景识别(诊断/计划/复盘/帮助)     │
│ 自由推理决策    │      │ → 剧本给出下一个工具调用          │
│               │      │ → 剧本走完后用模板渲染真实数字     │
└───────────────┘      └─────────────────────────────┘
```

Mock 的实现要点（`llm/mock_client.py`）：
- 从对话历史解析"当前回合已调用了哪些工具、结果是什么"；
- 按剧本（playbook）给出下一个 `tool_use`，全部执行完则渲染最终报告；
- **决策规则透明**：例如计划场景的动作选择规则是"月节省>0、舒适影响非 high、取前 5"；
- 复盘场景含**条件步骤**：总体达成率 <60% 或有动作 <40% 时，自动追加 `record_feedback` 写入反思记忆——展示了 Agent 的反思闭环。

## 4. 领域算法：数字从哪里来

### 4.1 负载分解（`domain/disaggregate.py`）

只有总电表读数，如何知道空调用了多少电？利用**时段特征 + 天气相关性**：

| 步骤 | 信号 | 归因 |
| --- | --- | --- |
| 1 | 工作日白天(09:00-16:00,无人在家)负载的 10 分位数 | 基线 = 冰箱+待机（按典型功率 58:42 拆分） |
| 2 | 工作日白天高于基线的小幅持续超额 | 热水器保温损耗（always-on 特征），推广到全天 |
| 3 | 夜间(22:00-07:30)扣除基线与保温后的剩余 | 空调（睡眠时段） |
| 4 | 周末下午高于工作日同时段 25 分位典型值的部分 | 空调（客厅） |
| 5 | 早晚洗澡时段(06:30/07:00/21:00/21:30)的短脉冲 | 热水器加热 |
| 6 | 晚间洗衣时段的尖峰（扣除照明电视典型值后 >0.2 kWh） | 洗衣机 |
| 7 | 其余 | 照明/厨房/娱乐等 |

**精度验证**：合成数据自带分电器真值，`eval-disagg` 输出逐类别 MAE（空调约 0.35 kWh/天，相对误差 ~3%）。已知局限（主动披露）：夜间热水器补热会被部分误记为空调；依赖"白天无人"假设。

### 4.2 节能模拟（`domain/simulate.py`）

每条规则 = 触发条件 + 有出处的经验系数：

| 动作 | 规则 | 系数出处 |
| --- | --- | --- |
| 空调 24→26°C | 空调日均 × 7% × 温差（受舒适约束限制目标温度） | NEA 节能宣传经验值 |
| 热水器改定时 | 热水器日均 × 40% | 储水式热水器保温损耗典型占比 |
| 冷水洗衣 | 洗衣日均 × 60% | 洗衣机能耗大头为加热水 |
| 断待机 | 待机日均 × 40% | 智能排插可消除比例 |
| 冰箱保养 | 冰箱日均 × 7% | 除霜/调温典型收益 |
| 错峰洗衣 | 仅分时电价下省钱（固定费率下如实标注"不省钱"） | 峰谷价差 |

输出三个维度：kWh/月、S$/月（当前电价）、kg CO2/月（电网排放因子 0.412 kg/kWh，EMA 口径）。

### 4.3 天气归一化追踪（`domain/tracker.py`）

```
CDH(制冷度时/天) = Σ max(0, 室外温度 - 26°C) × 0.5h

预期空调(新天气) = 基线期空调日均 × CDH_本周 / CDH_基线
无动作预期总量  = 基线日均 - 基线空调 + 预期空调(新天气)
实际节省       = 无动作预期总量 - 实际日均
```

再按"动作 ↔ 负载类别"映射（空调动作↔aircon 类等）给出**分动作达成率**。归因有噪声（分解误差会传导），报告中如实展示而非美化。

## 5. 记忆与状态设计

| 文件 | 内容 | 何时读 | 何时写 |
| --- | --- | --- | --- |
| `profile.json` | 画像 + 舒适硬约束 | 每次诊断/规划 | init / 用户反馈 |
| `plans.json` | 计划全部版本（含基线期、预期节省） | 复盘/追踪 | save_plan（旧版本自动归档） |
| `memory.json` | 用户反馈、复盘结论 | 每次规划前 | record_feedback |
| `reviews.json` | 复盘报告存档 | 报表 | review |
| `usage.csv` / `weather.csv` | 半小时电表/气温数据 | 所有分析 | init / simulate-week / 真实接口 |
| `usage_groundtruth.csv` | 分电器真值（Agent 不可见） | 仅 eval-disagg | 数据生成器 |

**为什么用文件而不是数据库**：课程项目规模下，可读、可diff、可演示（评审可以直接打开 JSON 看 Agent 记住了什么）比性能重要。

## 6. 合成数据生成器（`datagen/generate.py`）

按新加坡气候与 HDB 作息建模：日最高温 ~32°C 的正弦气温曲线；空调功率随室温上升；热水器 always-on 的保温脉冲（刻意埋下的低效点，等 Agent 诊断出来）；工作日/周末作息差异；所有随机源带种子（可复现）。

`simulate-week` 把当前计划的动作效果按**每日执行概率**（默认 0.85，模拟真实生活的不完美）注入未来 7 天——这让复盘环节有真实的"预期 vs 实际"差距可讲。
