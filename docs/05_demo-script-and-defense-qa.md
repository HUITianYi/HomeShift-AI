# 演示脚本与答辩 Q&A（20 分钟含问答）

> 建议分配：讲解 12 分钟 + 现场演示 4 分钟 + Q&A 4 分钟。
> 现场演示前务必彩排一遍（数据带固定种子，数字可复现）。

## 1. 演示流程建议（Presentation 结构）

### 开场（2 分钟）：问题与痛点
- 一句话定位："我们做了一个帮家庭省电费的 AI 智能体——Cut bills, not comfort。"
- 痛点：新加坡家庭月均电费 S$150+，空调等五类电器占 80%（NEA），但现有 App 只给账单和通用提示——**看得见总数，看不见原因，更没有跟踪调整**。
- 关键论点：这个问题**单次 LLM 调用解决不了**（要读数据、做计算、存状态、跨周迭代）——所以需要 Agentic AI。

### 系统概览（3 分钟）：什么让它 "Agentic"
- 放架构图（README 中的 mermaid 图）；
- 讲三层分工：**LLM 管推理决策，工具管事实计算，记忆管跨会话状态**；
- 用 30 秒过一遍 README 的“五阶段闭环”和“核心创新与思考”——这是直接回应课程主题的部分。

### 现场演示（4 分钟）：完整闭环
```
python -m homeshift diagnose        # 让观众看到工具调用轨迹逐条打印 —— "这就是 Agent 在自主工作"
python -m homeshift plan            # 强调：预期省 S$29.7/月，且尊重"孩子睡觉≤26°C"约束
python -m homeshift simulate-week   # 解释：模拟一周真实执行（85% 执行率）
python -m homeshift review          # 高潮：天气归一化、达成率 50%、空调没做到位 → 自动写入记忆
python -m homeshift report          # 收尾：打开 HTML 周报投屏
```
- 演示话术钩子："注意复盘报告——AI 没有报喜不报忧，它剔除了天气变凉的影响，指出空调动作只达成 20%，并且**自己把这个教训记了下来**，下次制定计划会先读这条记忆。这就是反思闭环。"

### 技术深挖（3 分钟）：挑一个讲透
推荐讲**负载分解 + 精度验证**（最有技术含量且直观）：
- 只有总电表，怎么知道空调用多少？→ 时段特征启发式（见
  `02_architecture-and-agent-principles.md`）；
- 怎么证明估得准？→ 合成数据带分电器真值，`eval-disagg` 显示空调 MAE 0.35 kWh/天（~3%）；
- 顺带展示工程判断：为什么所有数字不让 LLM 算（幻觉），为什么要做天气归一化（否则天气变凉会被冒功）。

### 收尾（1-2 分钟）：局限与展望
主动讲局限（这会加分，见 Q&A 部分），展望：接真实电表（connectors 已留好）、主动式 Agent（定时自动复盘推送）、多户学习。

## 2. 预期提问与回答（Q&A 预案）

**Q1：你们的数据是假的，这个系统有什么意义？**
> 数据是合成的，但有三点：(1) 合成器按物理与行为逻辑建模（气温-空调相关、作息、执行率），不是随机数；(2) 正因为合成，我们拥有真实世界没有的**分电器真值**，能定量证明负载分解算法的精度（空调误差 ~3%）；(3) 系统与数据源解耦，接真实电表只需实现 `connectors/meter_api.py` 一个函数，SP 集团 App 本身就能导出半小时数据。

**Q2：这和直接问 ChatGPT"怎么省电"有什么区别？**
> ChatGPT 给的是通用建议（"少开空调"）。我们的区别在于：(1) 建议基于**你家的**数据——先分解出你家空调占 62% 才建议改空调；(2) 数字可复算——省 S$14.2/月来自确定性模拟器而非模型口算；(3) 有闭环——一周后用实际电表数据验证，没做到的会被发现并调整。前者是知识问答，后者是持续运行的智能体。

**Q3：负载分解误差会不会误导用户？**
> 会有误差，我们做了三重防护：(1) 报告中明确标注"估算"并披露方法与局限；(2) 用真值定量评估，误差范围心中有数；(3) 复盘看的是**总量节省**（电表直接可测），分动作归因仅作参考。另外真实产品可以引导用户装 1-2 个智能插座对关键电器直接计量，逐步替代估算。

**Q4：为什么用 Mock 模式演示，是不是没接真的 LLM？**
> 真实 Claude 客户端已完整实现（可现场展示代码/切换），Mock 是**刻意的工程决策**：课堂演示不应依赖网络、密钥与预算，且 Mock 与真实模型走同一套工具循环、同一套计算，数字一致。区别只在"决策由剧本还是模型给出"。这恰好说明我们理解 Agent 的本质：能力在工具与闭环，LLM 是可替换的大脑。

**Q5：舒适约束怎么保证不被违反？**
> 双保险：(1) 约束在**工具层**硬编码生效——模拟器生成"空调调温"动作时目标温度取 `min(26, 用户上限)`，LLM 无法绕过；(2) 系统提示词将舒适约束列为不可违反的行为准则。有单元测试覆盖（用户限 25°C 时动作标题自动变为 25°C）。

**Q6：如果用户不执行计划怎么办？**
> 这正是复盘环节的价值：达成率会暴露执行问题，Agent 把"哪个动作没做到"写入长期记忆，下次规划会优先选择更容易坚持的动作（如把行为类动作换成一次性动作）。演示中可用 `--adherence 0.3` 模拟"懒人家庭"，看 Agent 如何反应。

**Q7：碳减排数字怎么算的？**
> 节省 kWh × 新加坡电网排放因子 0.412 kgCO2e/kWh（EMA 公布口径，配置可更新）。我们同时展示三个维度（钱/电/碳），让用户自选激励——研究表明对多数家庭"钱"最有效，但碳维度对可持续主题同样重要。

**Q8：多智能体呢？为什么只有一个 Agent？**
> 我们的判断：这个问题规模下，一个 Agent + 12 个工具是**正确的复杂度**——为了多智能体而拆分（如"诊断 Agent + 规划 Agent 互相对话"）只会增加延迟与失败面，不增加能力。架构上如果未来需要（如社区级多户协同错峰），LLM 抽象层与工具层可以直接复用。能解释"为什么不用"比盲目堆技术更重要。

**Q9：安全性考虑了什么？**
> (1) Agent 只有 12 个白名单工具，无文件系统/网络/代码执行权限，能力边界即安全边界；(2) 工具轮数上限防失控；(3) 不指导危险操作（改电路一律转介电工，写入系统提示词）；(4) API key 只从环境变量读取；(5) 真实模型的安全拒绝（refusal）有处理分支。

**Q10：这个项目一周做出来的，分工怎么说？**
> 建议按模块讲分工：数据与领域算法（datagen/domain）、Agent 与 LLM 层（agent/llm）、CLI 与可视化（__main__/report）、测试与文档。架构分层清晰，天然适合并行开发——这本身也是架构设计的收益。
