# 09 · Presentation 建议

教授的题目是 **"Agentic AI in X"**。这份文档回答三个问题：
我们够不够格叫 agentic？该怎么讲？会被问什么？

---

## 一、主题契合度：先说结论

**契合，但不是天然契合 —— 需要主动把"为什么这必须是 agent"讲出来。**

"Agentic AI in X" 这类题目最常见的失分点是：做了一个 **AI 功能**，
然后声称它是 agent。评审老师听过太多"我们用 LLM 做了个能源助手"，
真正会打动人的是 **"这个问题如果不用 agentic 架构就解决不了"**。

### 我们踩中了哪些 agentic 要素

| Agentic 要素 | 本项目的体现 | 证据在哪 |
| --- | --- | --- |
| **自主性** | LLM 自主决定调用哪个工具、调几次、什么时候停 | `agent/core.py` 的 tool-use 循环 |
| **工具使用** | 12 个工具，覆盖感知/分析/行动/记忆 | `agent/tools.py` |
| **环境交互** | 读真实电表、真实气温、真实电价，写回计划文件 | `realdata/`、`connectors/` |
| **规划** | 从诊断到多动作组合，含取舍与排序 | `domain/simulate.py` |
| **记忆** | 跨会话的结构化持久记忆（不是对话上下文） | `datastore/store.py` |
| **反思与自我修正** | 复盘 → 发现达成率低 → 写入记忆 → 下轮调整 | `domain/tracker.py` + `record_feedback` |
| **多角色协作** | 七个专职角色，其中一个持否决权 | `agent/roles.py` |
| **护栏** | 最大工具轮数、数字纪律、舒适否决、安全边界 | `prompts.py` + `domain/comfort.py` |

八项里我们有八项。**这个覆盖度是足够的**，问题不在有没有，而在怎么讲。

### 最值得强调的三个差异化点

其他组大概率也会做"LLM + 几个工具"。真正能拉开差距的是这三条：

**1. 数字纪律（LLM 不允许产生数字）**

这是整个项目最硬的设计约束。所有 kWh、金额、CO2 都来自确定性计算，
模型只负责决定"调用什么"和"怎么解释"。

为什么这值得讲：LLM 在能源、医疗、金融这类领域最大的风险就是编造数字。
我们的做法把 **可信度问题变成了架构问题**，而不是靠提示词祈祷。
而且这条约束是可验证的 —— 任何一个数字都能追溯到具体的计算函数。

**2. 舒适守门人有真正的否决权**

产品口号是 "Cut bills, not comfort"。我们有一个角色专门负责
**否决那些能省钱但会牺牲舒适的方案**，被否决的动作会带着理由展示给用户：

> "系统为保护你的舒适度，主动放弃了 S$9.00/月的可省金额。"

为什么这值得讲：这是 **价值对齐（value alignment）在产品层面的具体实现**。
大多数节能系统的隐含目标函数是"最小化电费"，我们显式地把舒适度做成了
硬约束而不是软惩罚项。让用户**看见系统为他放弃了什么**，
这是建立信任的关键设计。

**3. 系统会主动说出自己不知道的事**

这是这次改造中我最想让你重点讲的一条。系统在四种情况下会主动降级结论：

- 天气数据覆盖不足 → "本次未做天气归一化，数字包含气温影响，请谨慎解读"
- 分动作达成率异常（1100%）→ "这不可信，更可能是负载分解的归类误差"
- 没有分表真值 → "精度无法定量验证（真实家庭的常态）"
- 画像由曲线反推 → "这是假设，不是用户自述"

为什么这值得讲：**agentic 系统的最大风险是流畅地给出错误答案**。
一个会说"我这里不确定"的 agent，比一个永远自信的 agent 有用得多。
这也是我们和"套壳 ChatGPT"最直观的区别。

## 二、20 分钟演讲设计

### 结构（建议时间分配）

| 时长 | 章节 | 目标 |
| --- | --- | --- |
| 2 min | 问题：账单看得见，原因看不见 | 让听众有代入感 |
| 2 min | 为什么这必须是 agent，而不是一个 dashboard | **立论** |
| 3 min | 架构：七个角色 + 数字纪律 | 讲清楚设计 |
| 6 min | **现场演示** | 全场重心 |
| 3 min | 我们如何验证自己是对的 | 学术可信度 |
| 2 min | 局限与未来 | 主动暴露弱点 |
| 2 min | 收尾 | 一句话记忆点 |

### 开场（别用"随着人工智能的发展……"）

建议这样开：

> "一张新加坡家庭的电费单会告诉你这个月用了 543 度电。
> 它不会告诉你其中 26% 是冰箱、19% 是根本没人在用的待机负载、
> 还有一部分是热水器整天保温白白散掉的热。
> 我们的用户不缺数据，缺的是**有人替他把数据变成决定**。"

然后立刻抛出立论：

> "这件事为什么需要 agent，而不是一个仪表盘？因为它不是一次查询，
> 是一个持续的循环：诊断需要多步推理、方案需要在省钱和舒适之间取舍、
> 而且**一周之后必须回来检查自己错在哪并调整**。
> 仪表盘做不到第三步。"

### 演示流程（6 分钟，务必提前跑通并录屏备份）

```bash
# 0. 演示前准备（不要在台上做）
python fetch_real_data.py
python -m homeshift diagnose && python -m homeshift plan
python -m homeshift simulate-week && python -m homeshift review
python -m homeshift export-web
```

台上按这个顺序：

| 步骤 | 命令 | 讲什么（一句话） |
| --- | --- | --- |
| 1 | `status` | "这是真实数据，不是我们编的 —— 数据集、许可、完整度都在这" |
| 2 | `agents` | "七个角色，自检确保没有工具无人认领" |
| 3 | `diagnose` | **让工具调用一行行滚出来** —— "注意左边是哪个角色在出手" |
| 4 | `plan` | "重点看这里：有一条动作被舒适守门人否决了，理由写在这" |
| 5 | `review` | "上周的预测错在哪，系统自己承认了" |
| 6 | `eval-disagg` | "我们的算法有多准？这是对照真实分表算出来的误差" |
| 7 | 网站 | "同一份数据，队友的可视化" |

**第 3 步是全场最有价值的 30 秒** —— 工具调用逐行滚动的画面是
"这是个 agent"最直观的证据。不要跳过，不要加速。

**第 5 步是最反直觉但最加分的一步**：主动展示自己预测错了。
台词建议：

> "上周我们预测冰箱保养能省 0.34 度/天。实际测出来是 3.74 度，
> 达成率 1100%。听起来是好消息 —— 但系统把它标成了'归因不可信'，
> 因为这几乎肯定是负载分解把别的负载算进了这一类，而不是用户真的
> 超额完成了 11 倍。**一个会怀疑自己好消息的系统，才敢让人用。**"

### 收尾

> "我们没有做一个更聪明的聊天机器人。我们做的是一个
> **敢说自己不知道、并且会为了你的舒适主动放弃省钱机会的** agent。
> Cut bills, not comfort."

## 三、预期提问与回答

### Q1：这跟直接问 ChatGPT "怎么省电" 有什么区别？

> ChatGPT 会给你十条通用建议。我们会告诉你**你家**冰箱占 26.7%、
> 待机占 19.3%，做这四件事每月省 19.21 元，其中一件因为你孩子怕热被否决了，
> 一周后再告诉你哪件没做到。
>
> 更根本的区别是：ChatGPT 会编数字，我们的架构不允许模型产生任何数字。

### Q2：你们的负载分解准吗？

**这是最可能被问的技术问题，必须准备好。**

> 我们选 UCI 数据集就是为了能回答这个问题 —— 它自带三路分表真值。
> `eval-disagg` 会输出每个类别的平均绝对误差。
>
> 但我要诚实说明两点：第一，数据集的分表口径和我们的类别不完全对应，
> 比如它的 2 号分表把冰箱和洗衣机混在一起，所以冰箱没有独立真值，
> 我们把这些口径不匹配显式记录在 `provenance.json` 里；
> 第二，这份数据来自法国温带地区，而我们的启发式是按热带气候设计的，
> 所以"空调"那一类在这份数据上实际混合了取暖和其他负载。
>
> 真实场景里家庭只有一块总表，本来就没有真值可对 —— 这正是负载分解
> 要解决的问题。我们能做的是把不确定性显式呈现，而不是声称 95% 准确。

### Q3：为什么是七个 agent？不是营销包装吧？

> 可以现场跑 `python -m homeshift agents`。每个工具都归属于一个角色，
> 有一个自动化测试专门防止出现"没被任何角色认领的工具"——
> 刚才这个自检就抓到过一个漏网的工具。
>
> 架构上准确的说法是 **single-controller multi-role**：
> 一个编排器决定下一个该谁出手，七个角色各自持有自己的工具和职责。
> 我们没有让七个角色各跑一个独立 LLM 会话，因为那样贵七倍，
> 而且数字容易互相打架。

### Q4：如果模型编造数字怎么办？

> 架构上它没有机会。所有数字来自 `domain/` 里的确定性函数，
> 模型看到的是工具返回的 JSON。你可以随便挑一个数字，
> 我现场把它追溯到具体的计算函数。
>
> 另外我们连离线 Mock 模式的报告模板都改成了数据驱动 ——
> 之前有个版本会写"空调是绝对大头"但数据显示只占 3.3%，
> 那种自相矛盾我们专门修掉了。

### Q5：用户会真的照做吗？行为改变很难。

> 这正是我们做七天清单和达成率追踪的原因。系统假设用户**做不到 100%**，
> `simulate-week` 默认执行率就是 85%。复盘时会分动作算达成率，
> 哪条没做到就换成更容易坚持的。
>
> 舒适守门人也是为这个服务的 —— 让人放弃睡眠质量去省 9 块钱，
> 第三天就会放弃整个计划。

### Q6：数据隐私怎么办？家庭用电数据很敏感。

> 三层：第一，系统可以完全离线运行（Mock 模式或本地 Ollama），
> 数据不出本机；第二，发给模型的是聚合后的统计量，不是逐条读数；
> 第三，密钥只从环境变量读，不写进任何配置文件。

### Q7：商业上怎么落地？

> 最直接的是电力零售商的增值服务 —— 新加坡开放电力市场后零售商在拼差异化，
> 帮用户省电反而能提高留存。第二条是智能电表/家庭能源硬件厂商的软件层。
> 但我要说清楚这不是我们这次的重点，我们做的是可行性验证。

### Q8（可能来自懂技术的老师）：为什么不用 LangChain / AutoGen？

> 因为这个项目的核心难点不在编排框架，在**领域正确性** ——
> 负载分解怎么做、天气怎么归一化、哪些结论不可信。
> 框架帮不上这些忙，反而会让"数字纪律"这条约束难以强制执行。
>
> 而且零依赖对课程演示有实际价值：评审电脑不用装任何包就能跑。

## 四、给队友分工的建议

如果是三个人：

| 角色 | 讲什么 | 时长 |
| --- | --- | --- |
| A（产品视角） | 问题、立论、收尾 | 6 min |
| B（工程视角） | 架构、现场演示 | 9 min |
| C（可视化） | 网站演示、验证与局限 | 5 min |

**关键**：B 和 C 展示的必须是**同一份数据**。
后端跑完 `export-web` 把 `data/web/` 交给 C，两边数字一致。
如果台上出现"网站显示 146.08、终端显示 164.06"，前面讲的都白费了。

## 五、必须主动承认的局限（不要等着被挑出来）

放在演讲倒数第二部分，用一页 slide 列出：

1. **负载分解是启发式，不是机器学习**。选它是因为可解释、可讲清楚原理，
   代价是精度上限有限。下一步可以用带真值的数据训练一个监督模型。
2. **领域假设与数据来源不完全匹配**。热带假设 + 温带数据，
   已在系统内显式标注，但这确实是当前版本的局限。
3. **家庭画像是反推的**。真实产品里应该由用户填写，
   我们标注了哪些是观测、哪些是假设。
4. **只有单户长周期数据，没有跨户泛化验证**。
   我们不知道这套启发式在一百个不同家庭上表现如何。
5. **没有闭环控制**。系统只建议不执行，这是刻意的产品边界 ——
   但也意味着效果完全依赖用户执行。

主动说这些不会扣分，反而会加分。**评审最怕的是学生不知道自己不知道什么。**
